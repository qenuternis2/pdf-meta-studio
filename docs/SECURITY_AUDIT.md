# End-user security audit

Reviewed on 2026-10-07, against maintenance baseline `482aff1f1f7377c512453ad7698ed8c2fbedce9d` and the changes described below. Scope: application/worker sources, shipped dependencies, installer generation, build/download scripts, CI and release/update paths. Source review preceded execution. Dynamic checks used the isolated cloud checkout, synthetic files and the existing qpdf corpus; no user documents or downloaded exploit payloads were used.

Risk levels below describe this application's exposure, not an upstream CVSS score. An affected dependency version does not establish that every advisory's vulnerable operation is reachable here. This is a bounded review, not a proof that the application is safe.

## Confirmed findings and corrections

### S1 — Temporary output was reopened through a replaceable path (high, conditional local attack)

- **Location:** `worker/src/fileutil.cpp`, former `tempPathIn`; `worker/src/pdf_edit.cpp`, `saveEdits`/`QPDFWriter`; `worker/src/private_data.cpp`, `exportMetadata` and `exportPrivate`.
- **Cause:** exclusive creation reserved a temporary name but immediately closed the file. PDF writing and exports then reopened that name, following a substituted link. Exclusive creation alone did not protect the later write (CWE-367).
- **Conditions/damage:** an attacker able to modify the output directory can substitute the temporary name between reservation and reopening. On POSIX, this can truncate another file writable by the victim. Windows exploitation also depends on reparse-point/directory permissions. A deterministic isolated reproduction using the baseline production reservation function and export write pattern overwrote an unrelated synthetic sentinel through a substituted symlink. An end-to-end concurrent Windows exploit was not demonstrated.
- **Minimal correction applied:** `TemporaryFile` retains the exclusively created `FILE*`; qpdf receives that stream without owning/closing it, and exports write through the same stream. Flush and verification precede commit. Windows denies other readers, writers and deletion while the descriptor is held; verification uses that same stream. Cleanup retains the existing failure behavior. The old native helper signature remains available for compatibility, but production writers no longer use it.
- **Regression:** `worker/tests/helpers/secure_temporary_file.cpp` deterministically substitutes the pathname on POSIX and verifies that the sentinel is unchanged and PDF verification reads the original descriptor. Its Windows branch checks denied rename/second writer and successful qpdf stream verification with the write handle retained. `test_secure_temporary_file_descriptor_and_permissions` runs the helper. The first MSVC run exposed incompatible `_wfopen_s` filename-reader sharing; verification was corrected to use the stream reader, without relaxing the write/delete protection.
- **Boundary:** serialization and PDF verification use the retained descriptor; protection transfer and final commit still use names. This does not make an attacker-controlled directory tree safe: the final close/rename has a remaining race window. Hostile ancestors, reparse points, network filesystems and concurrent commit replacement need separate directory/handle-based hardening and tests.

### S2 — Windows temporary output inherited broader directory access (medium, confidentiality)

- **Location:** `worker/src/fileutil.cpp`, former `tempPathIn`/`CreateFileW`; `carryOverProtection` at the end of PDF/export writes; `src/PdfMetaStudio.Core/DocumentService.cs`, `OpenAsync` snapshot copy/ACL order.
- **Cause:** default security attributes inherited the destination directory DACL. Source/target protections were transferred only after writing the document or plaintext export (CWE-377/CWE-732). Managed snapshots also reapplied an unmodified loaded `FileSecurity`; [.NET persists only changed sections](https://github.com/dotnet/runtime/blob/v10.0.12/src/libraries/System.IO.FileSystem.AccessControl/src/System/Security/AccessControl/FileSystemSecurity.cs), so the intended snapshot DACL transfer was a no-op.
- **Conditions/damage:** a restricted document saved in a shared directory could expose intermediate bytes to another account allowed by the inherited DACL. A separately configured shared Windows TEMP root can similarly expose a completed snapshot after its exclusive handle closes: the original no-op left inherited permissions in place. The Windows regression confirmed loss of the protected source DACL; a real second-account read exploit was not attempted. Normal private per-user TEMP mitigates exposure. Administrators and another process running as the same user are outside this protection's boundary.
- **Minimal correction applied:** create the pending Windows worker file with a protected, explicit current-user-only DACL before writing any bytes. POSIX retains exclusive creation with mode `0600`. For managed snapshots, copy the source access descriptor into a fresh `FileSecurity` explicitly marking that section changed, then apply it before writing document/zone bytes while both acquired write handles retain `FileShare.None`; this also protects partial/cancelled copies. Acquire the zone write handle before applying a read-only source DACL. Native output finishes zone writes under its private temporary DACL before final protection transfer. Legitimate read-only documents retain their Mark-of-the-Web and final source/target protections remain the intended policy.
- **Regression:** the Windows helper makes only its synthetic fixture directory broadly inheritable, then checks that the pending file has one explicit creator ACE and a protected DACL. `SnapshotPreservesProtectionAndBytesAndIsCleanedUp` exercises actual snapshot creation and edited-copy save from a protected read-only source DACL with Mark-of-the-Web (Windows), mode preservation (POSIX), byte equality, cleanup and source retention. Its first Windows run failed on the original no-op descriptor transfer, demonstrating the regression detector. These check descriptors/functional behavior; a real second-account access test, snapshot close-window race and non-elevated NTFS acceptance remain separate requirements.

### S3 — Pinned Expat lacked published security fixes (medium, malicious XMP/resource exhaustion)

- **Location:** `scripts/deps.lock`, Expat `R_2_7_1`; `worker/cmake/XMPCore.cmake` and `worker/src/xmp_model.cpp`.
- **Evidence/exposure:** official Expat release notes and CVE records identify fixes after 2.7.1, including memory amplification (CVE-2025-59375), quadratic attribute processing of well-formed XML (CVE-2026-66046/CVE-2026-76641), and invalid UTF-16 surrogate handling (CVE-2026-93990). PDF metadata is attacker-controlled. XMP is capped at 64 MiB; DTD/entity declarations and general entities are disabled, and the worker has resource/deadline limits. These mitigate several advisory paths, but do not justify retaining an affected parser. No arbitrary-code-execution exploit in this integration was established. Advisory conditions such as `XML_UNICODE`, 32-bit builds or incorrect direct `XML_ParseBuffer` usage must not be attributed to this x64 integration without evidence.
- **Approved correction applied:** Expat 2.9.0, verified tag commit `a76b1174c1ea52abb639a4c69d52b630a8a106a2`. Use upstream Expat's CMake target and generated platform configuration so new source/entropy helpers are included. Static linkage, disabled DTD/general entities and Adobe's `BanAllEntityUsage` remain in place. License inventory is updated.
- **Regression:** existing XXE/DTD and decompression-limit tests remain enabled; XXE testing uses only a synthetic entity file and also checks UTF-16 LE/BE, which bypass the ASCII precheck. A small paired valid/invalid UTF-16 XMP test confirms valid input still works and an unpaired surrogate is rejected. No high-memory public exploit was run.
- **Residual:** upstream explicitly tracks [unfixed non-public issues](https://github.com/libexpat/libexpat/issues/1160). A current version is not a guarantee of complete parser safety.

### S4 — Self-contained .NET runtime was behind security servicing (medium, maintenance exposure)

- **Location:** `global.json` pinned SDK 10.0.100; `src/PdfMetaStudio.App/PdfMetaStudio.App.csproj`/`scripts/build-windows.ps1` publish self-contained Windows runtimes.
- **Evidence/exposure:** the baseline published configuration embedded `Microsoft.NETCore.App` and `Microsoft.WindowsDesktop.App` 10.0.0. Microsoft's release metadata and runtime advisories describe later security fixes. Updating .NET installed on the user's PC does not patch those bundled runtimes. The supported Windows runtime version range in CVE-2026-32175 includes that baseline, but this review did not establish its exact trigger in this application's file operations.
- **Applicability:** Linux diagnostics/packaging ACL advisories do not establish a vulnerability in the Windows product. The application does not use COSE, `TarFile.ExtractToDirectory`, `EncryptedXml`, HTTP/QUIC servers or DiaSymReader/PDB parsing; their advisory conditions were not demonstrated here.
- **Approved correction applied:** SDK 10.0.112 within the existing 10.0.1xx family; official release metadata associates it with runtime 10.0.12. Limit `rollForward` to `latestPatch`: the prior `latestFeature` policy let Windows CI select SDK 10.0.401 despite the 10.0.112 version entry. Linux build and managed tests run with 10.0.112; Windows must exercise that same approved family. The Windows package's actual runtime configuration must be checked, separately from NuGet's package advisory query.

### S6 — Backup cleanup was armed before exclusive creation succeeded (medium, concurrent data loss)

- **Location:** `worker/src/pdf_edit.cpp`, `saveEdits` backup setup and `TempGuard` destructor; `worker/src/fileutil.cpp`, `uniqueSibling`/`copyFileExact`.
- **Cause/conditions:** two saves or another writer can claim the same candidate after the existence check. `copy_file` correctly refuses overwriting it, but the pre-armed failure guard would then delete that other writer's file. This is a confirmed ownership/order error; an end-to-end concurrent race was not executed. It can destroy a legitimate recovery backup despite refusing the second save.
- **Minimal correction applied:** arm backup cleanup only after the exclusive copy returns successfully. Existing replacement/backup and cancellation tests cover successful ownership and failure cleanup; concurrent collision and disk-full/partial-copy cases still require isolated stress checks. When ownership cannot be established after a failed copy, avoiding deletion takes precedence over removing a possible partial backup.

## Reviewed trust boundaries and behavior

- **Commands/processes:** `src/PdfMetaStudio.Core/Protocol/WorkerClient.cs` launches the adjacent worker with `UseShellExecute=false`; PDF paths/passwords travel through redirected JSON stdin. `ProfileValidator.cs` uses `ArgumentList`, not interpolated shell commands, and bounds output/time. No product `cmd`, PowerShell, `system` or shell-based user-input execution was found. The user-selected EXE/JAR is trusted executable code with the user's rights; Java is resolved through the user's PATH. The application does not download it or sandbox it. Review/error messages can contain local paths or diagnostic metadata; a user sharing a report should inspect it first.
- **Files/deletion:** save replacement requires the appropriate mode, rechecks fingerprints and verifies a backup; copy/export targets are intentionally selected paths, not a fixed allowed root. The stdin protocol is an internal child-process interface, not an authenticated filesystem broker or local HTTP service. `DocumentService.cs` creates snapshot directories and cleans its own tracked snapshots on normal disposal. A crash can leave document duplicates on disk; retention/cleanup policy is a remaining privacy/disk-space concern. Source encryption remains in raw PDF snapshots, while an explicitly requested metadata/private export can contain plaintext. The application is a metadata editor, not a PDF active-content sanitizer: opaque JavaScript/actions/attachments can remain in saved PDFs but are not executed by this editor.
- **Privileges/install:** application and worker manifests request `asInvoker` with `uiAccess=false`. `installer/generate.py` emits a per-user LocalAppData/HKCU MSI without service, startup registration, privileged custom action or network installer step. Empty-directory removal is not recursive deletion of user documents. No administrator requirement was introduced. Native Windows Job limits restrict resources, not privileges or filesystem/network access.
- **Privacy/secrets:** no application telemetry/upload client, browser scraping, microphone/camera access or clipboard harvesting was found. Normal WPF user-initiated copy/paste remains available. PDF passwords are masked and passed over stdin, not process arguments, stored settings or intentional request logs. They remain in managed/native process memory; immutable strings are not guaranteed to be zeroized. The worker client retains a bounded stderr tail for local failure diagnosis. A tracked-file secret-pattern search found no matching private-key/token material; all-history secret scanning was not performed.
- **Networking/XML:** no product listener, local HTTP API, remote WebView or Electron host exists. The UI is WPF, with no downloaded web content or browser IPC. Optional validator reports use `XmlReader` with prohibited DTDs, a null resolver and a character cap. Build sources use HTTPS with normal certificate verification; no verification-bypass flag was found. End-user archive extraction is absent. Build-only Poppler extraction verifies the pinned SHA-256; license/package archives come from the reviewed build download paths.
- **Build/CI:** `windows.yml` has read-only build permissions and a separate release job with content-write permissions; no `pull_request_target` execution of fork changes was found. Native dependency tags are checked against full commits. Desktop preparation's registry/process manipulation is CI-only test infrastructure guarded by `GITHUB_ACTIONS`, not installed product code; that environment flag is a convenience guard, not a security boundary. Those scripts were not run against a user's working Windows installation.
- **Update mechanism:** there is no automatic updater, downloaded-plugin execution or background update service. Updates are manually obtained GitHub releases/MSI upgrades. ZIP/MSI SHA-256 manifests detect corruption but do not independently authenticate the publisher; an attacker controlling the release channel can replace assets and checksums together.

## Recommendations requiring a separate decision

These are remaining trust assumptions or possible attack surfaces, not demonstrated new remote-code-execution vulnerabilities:

| Priority / location | Conditions and potential damage | Minimal next step |
|---|---|---|
| High defense-in-depth: `WorkerClient.cs`, `worker/src/main.cpp` | A native parser exploit, if one exists, would execute with the user's file/network rights; a separate process and 4 GiB memory limit are not an OS security sandbox | Design an approved restricted-token/AppContainer or broker boundary and test all authorized read/save/export paths before changing behavior |
| Medium authenticity: release job, MSI/EXE | Compromised download/release access can substitute executable assets; releases currently lack an independent publisher signature | Owner-provided Authenticode signing and/or independently verifiable release attestations; agree installer/update trust policy before changing it |
| Medium supply chain: `windows.yml`, build scripts | Unhashed package restoration or a modified local tool checkout could compromise builds; immutable Action pins do not establish that upstream code is trustworthy | Keep Action updates explicit and review their commits; consider package locks/hashes and tool-version validation. Run builds in disposable environments, retaining TLS/commit/checksum verification |
| Medium conditional release labeling: release job | An existing tag supplied to a manual release could identify a different source commit from the assets being published; no actual mismatch or compromise was found | Verify an existing tag resolves to the built SHA before publication; agree release failure behavior before altering it |
| Medium privacy: `DocumentService.cs`, snapshots | Crash leftovers or many open documents retain extra local PDF copies and consume disk space; per-user access does not protect against the same user/admin | Agree bounded retention and safe stale-session cleanup without deleting recovery material or another running session's files |
| Medium conditional at-rest privacy: `DocumentService.cs`, snapshot creation; `fileutil.cpp`, copy output | EFS-encrypted source files are read transparently as plaintext. Stream-created snapshots/output in a destination that does not itself inherit EFS encryption do not explicitly preserve that filesystem encryption; DACLs and PDF encryption are separate protections. This code-path risk was not verified with an EFS-enabled Windows fixture | Isolated EFS/unencrypted-TEMP/unencrypted-destination checks, then agree an encrypted working-storage/output policy. Do not silently generate EFS certificates or change storage behavior |
| Medium local filesystem boundary: `fileutil.cpp` | An attacker controlling parent directories/reparse points or the final close/rename window can still interfere with commit/verification | Isolated concurrent-rename/reparse/SMB tests, then approved handle-relative directory/commit hardening where supported |

## CI hardening follow-up — 2026-10-08

All five external Actions in `.github/workflows/windows.yml` are pinned to full upstream commit IDs resolved from their existing `v4`/`v5` tags, without upgrading Action major versions. The comments retain the upstream tag for review; future updates must explicitly review and change the SHA. This prevents movement of those tags from silently changing build code, but does not independently prove the pinned code or downloaded packages safe.

Every checkout sets `persist-credentials: false`, so its GitHub token is not left in the checkout's Git configuration for later build/test processes. Explicit artifact/release token access and the existing job permissions are unchanged. This reduces unnecessary token exposure; it does not isolate untrusted job code from all GitHub Actions credentials.

## Validation and limitations

- Baseline managed tests: 84 passed with the real worker and IPC test peer. The isolated baseline reservation/reopen reproduction confirmed sentinel overwrite; it was not performed on user data.
- After the descriptor/DACL, snapshot-order and approved dependency changes: Release build succeeded with SDK 10.0.112, zero warnings/errors; 85 managed tests passed, zero skipped. Linux native suite: 48 passed, 5 platform/environment skips. Corpus: 628 files, 586 opened, 470 saved, zero failures. Seven malformed/encryption samples were intentionally blocked by post-write verification; password, damage, permission and unsupported-profile refusals are reported separately. The encryption test also independently decrypts the AES-256 output through pypdf/cryptography.
- Independent pypdf/Poppler comparison after the stream-reader correction: 420 files passed complete-page rendering and structure/field/attachment comparisons; 208 files were explicitly excluded or refused; zero failures. See [the isolated Linux evidence summary](validation/security-audit-linux.json) for counts, versions and limits.
- Full-solution transitive NuGet advisory query found no listed vulnerable packages; warning-level managed analyzers and Python/Bash/PowerShell syntax checks passed. Actual Windows x64 publish metadata on Linux contains both frameworks at 10.0.12; this is compilation/package evidence, not Windows execution evidence.
- Windows-specific native, actual packaged runtime, GUI and MSI evidence is retained in [the security PR and its CI checks](https://github.com/qenuternis2/pdf-meta-studio/pull/12). Read the successful tested revision and its native/TRX/host/GUI/installer artifacts rather than inferring those results from Linux compilation or earlier runs. The full workflow uses a Windows Server MSVC build and a separate Windows 11 ARM64 VM executing the x64 application under emulation.
- Still needed: non-elevated Windows 11 x64/offline installation; real second-account NTFS access; hostile reparse/SMB/concurrent-commit checks; stale-snapshot recovery/cleanup; publisher-signature verification if signing is introduced. GUI/installer checks execute only in disposable Windows CI VMs with synthetic fixtures.
- The review did not fuzz every parser, execute resource-exhaustion exploit corpora, scan complete Git history, prove all transitive/toolchain components free of CVEs, or establish the absence of malicious upstream code. Unknown advisories and newly published fixes remain possible.
- Previously published v0.3.0 assets predate these corrections. Changes in `main` and new CI packages do not retroactively patch an already downloaded release; a serviced release needs its own publication/version decision.
